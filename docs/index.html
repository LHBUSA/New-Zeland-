Country API architecture

One global edge. One deep New Zealand contract.

PropData keeps one global API surface while preserving country-native data models underneath it. New Zealand requests carry country=NZ; the resolver then routes into New Zealand-specific property identity, title, cadastral and physical-improvement intelligence. The country site and workspace are the focused developer experience for that market—not a separate disconnected backend.

01 · RESOLVEAddress / parcel / coordinates

Resolve the input against authoritative New Zealand identity instead of forcing a U.S. parcel convention.

02 · CONNECTParcel ↔ title ↔ building

Preserve the many-to-many title graph and spatial building relationships around the verified parcel.

03 · ENRICHCountry-native context

Attach available geometry, derived physical context and legal/statutory layers with independent coverage states.

04 · DELIVERREST · MCP · bulk · custom

Use the same governed PropData account and provenance rules across delivery modes.

Blueprint: this is the country pattern moving forward—global PropData API → country adapter → country website → country docs → country workspace. The global product stays unified while each mature market gets a genuinely deep local developer experience.

Authentication

Credentials stay server-side.

Direct REST uses the x-api-key header. Production keys belong in server-side secrets or environment variables—not URLs, browser bundles, screenshots, analytics, or repositories. The NZ Workspace is an account/developer tool and only sends a key after the user explicitly connects one for the session.

ENVIRONMENT
PROPDATA_API_KEY=pd_live_...
PROPDATA_API_BASE=https://propdata-api-worker.sales-fd3.workers.dev
MCP is different. PropData MCP uses OAuth in compatible clients. Do not paste a static REST API key into an MCP authorization flow.

Legal property identity

Titles stay relational.

PropData does not flatten New Zealand title identity into a single fake owner field. The graph preserves title records and title↔parcel associations separately so multi-title, unit-title and shared-spatial contexts remain structurally correct.

VERIFIED TITLE-SHAPE EXAMPLE
{
  "title_no": "1006231",
  "status": "LIVE",
  "title_type": "Unit Title",
  "land_district": "Wellington",
  "issue_date": "2021-11-01T16:20:02Z",
  "guarantee_status": "Guarantee",
  "estate_description": "Stratum in Freehold, 1/1, Unit 44 Deposited Plan 90777",
  "number_owners": 1,
  "spatial_extents_shared": true,

}
Named ownership is a separate entitlement problem. Title metadata and number_owners do not authorize inference of named owner identity. LINZ Personal Data Licence-gated datasets, including the Title Memorial List, remain separately controlled.
Physical property graph

Buildings are linked, not merely nearby.

The national building-outline source baseline contains 3,268,141 records. PropData then builds a separate relationship graph with 3,820,845 building↔parcel links. The relationship model preserves method, confidence basis, overlap area, overlap ratio, metric CRS and geometry-repair provenance where applicable.

A complete national building source does not mean every parcel contains a building. A zero relationship count is different from unavailable linkage coverage; read the returned coverage state.

Do not guess

Match, coverage and provenance are separate signals.

match_level

How the input resolved: address, parcel, coordinate or another explicit identity method.

coverage_status

Whether the requested source/layer is available for the resolved context.

parcel_resolution

Whether an address or coordinate successfully attached to parcel identity.

source / provenance

Where the fact originated and how a derived relationship was produced.

count / returned / truncated

Distinguish total matches from bounded response items.

null / unavailable

Missing source truth remains missing. PropData does not convert absence into a favorable claim.

Core contract rule: base identity success and enrichment availability are not the same thing. Treat optional country layers independently so a missing enrichment never corrupts a valid property match.
Operational behavior

Handle failures by category.

StatusMeaningRecommended behavior
400Validation / invalid requestCorrect parameters before retrying.
401Authentication failedCheck the server-side credential and account status.
403Entitlement / access restrictionDo not retry blindly; verify plan or restricted-layer entitlement.
404Route or supported resource not foundDistinguish route mismatch from a property no_match response.
429Rate limitUse backoff and authoritative usage/rate-limit signals.
5xxTransient service/upstream failureRetry conservatively; preserve a successful base property response if only an optional enrichment failed.
Source and rights transparency

Authoritative sources in. Governed delivery out.

Core New Zealand property layers are sourced from Toitū Te Whenua Land Information New Zealand (LINZ). PropData operates the ingestion, normalization, canonical identity, spatial processing, relationship graph, refresh automation, coverage semantics and production delivery above those source systems.

LINZ SOURCE-AWAREPROPDATA NORMALIZEDPERSONAL DATA ENTITLEMENTS SEPARATE
Title Memorial List / personal data: restricted LINZ personal-data datasets remain separately entitlement-gated. PropData does not represent those layers as generally available unless the applicable LINZ licence and downstream controls are in place.

PropData is an independent product of PropTechUSA.ai and is not operated by or affiliated with LINZ or the New Zealand government.
